# Consent Flow Plan

Дата: 2026-05-14

Статус: подготовлено, но пока не включено в боевой поток.

Цель: закрыть юридический риск без ухудшения тестового режима и без ложного проставления согласия.

## 1. Принцип

Пока проект на тестировании, мы:
- не включаем обязательный экран согласия в ежедневный поток
- не проставляем `consent_given=True` автоматически

То есть текущее безопасное состояние:
- согласие по умолчанию `False`
- бот не делает вид, что документ уже получен

## 2. Что нужно включить позже

### 2.1 При добавлении первого фото ученика

Перед сохранением эталонного фото:
- показать экран подтверждения

Текст:
`Подтверждаете, что письменное согласие родителя на обработку биометрических ПДн получено?`

Кнопки:
- `✅ Да, согласие получено`
- `❌ Нет, вернуться`

Без подтверждения:
- фото не сохраняется как эталон

### 2.2 При добавлении дополнительного фото

Если у ученика `consent_given=False`:
- снова спросить подтверждение

Если `True`:
- не спрашивать повторно

## 3. Что хранить

Текущего `Student.consent_given` мало для аудита.

Желательно добавить:
- `consent_confirmed_at`
- `consent_confirmed_by`
- `consent_note` nullable

Тогда будет видно:
- когда отметили
- кто отметил

## 4. UI-подсказки

В карточке ученика:
- если фото есть, а согласия нет: `⚠️ нет подтверждённого согласия`

В списке проблемных учеников:
- отдельный фильтр `без согласия`

## 5. Что не делать

Не делать:
- автоматическое `consent_given=True`
- скрытое подтверждение без явного шага
- сохранение плохого/сырого статуса “по умолчанию да”

## 6. Когда включать

Включать перед:
- реальным пилотом на детях
- масштабированием на новые организации
- запуском более формального parent flow

## 7. Порядок внедрения

1. добавить поля аудита в БД
2. добавить UI-подтверждение в add/edit photo flow
3. показать предупреждение в карточке ученика
4. включить blocking mode только после согласования продукта
